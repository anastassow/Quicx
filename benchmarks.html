03 — Throughput

Tasks per second

Full round-trip: producer submits task → broker ACKs → worker executes → done. Higher = better.

End-to-end throughput (tasks/sec, loopback)

Quicx: measured live — 20,000 tasks, 4 producers+workers, 64B payload.

Redis LPUSH/BRPOP raw: redis-benchmark figures for list operations.

06 — PMAD Configuration

10 MB pool layout used in this benchmark

The pool is split into 6 size classes. Distribution is weighted toward 64 B and 128 B because those cover the Task struct (64 B, static_assert-verified) and typical 64 B task payloads.

Size class allocation — 10 MB total

quicx_bench.conf — percentages must sum to 100

2.5 MB → ~36,000 blocks

2.5 MB → ~9,400 blocks

Task struct = 64 bytes (static_assert in queue.h). Worker struct = 32 bytes (static_assert in workers.h). Both go into their exact size classes with zero fragmentation. Payload (64 B in this bench) goes into the 64 B class alongside Connection structs. The 30% for 128 B handles Connection overhead + metadata.

Sources & methodology

  1. Quicx numbers — measured on this machine. Benchmark: bench_quicx.py against ./quicxd start --config quicx_bench.conf. 20,000 tasks, 4 producers, 4 workers, 64 B payload, loopback TCP (port 16381). Two runs: 21,436 tasks/sec and 22,312 tasks/sec. RSS via ps axo rss. Latencies collected per-task with time.perf_counter().
  2. Redis idle RSS. INFO MEMORY used_memory_rss on a fresh Redis 7.x instance. Typical: 1–3 MB used_memory, OS RSS 6–10 MB (jemalloc arena pre-allocation). Source: redis.io/docs/info.
  3. Celery worker memory — 100–300 MB per child. Community measurements (Back Market engineering blog, multiple Stack Overflow threads). Celery prefork forks one child per CPU core; each child loads the full application. Source: celeryq.dev/configuration.
  4. Celery throughput — 500–1,200 tasks/sec. Judoscale autoscaler docs, various community benchmarks (prefetch_multiplier=1, no-op tasks, JSON, Redis broker, single node). Source: judoscale.com.
  5. Beanstalkd performance. igvita.com benchmark + beanstalkd FAQ: "thousands of jobs/sec"; ~10,000 ops/sec with binlog. Memory: hundreds of KB idle, ~100 MB for 100,000 queued jobs. Source: beanstalkd.github.io.
  6. RQ throughput — 2,000–3,500 tasks/sec. Derived from RQ GitHub discussions and community reports. RQ is lighter than Celery (no Kombu, no chains) but still pays the full Python interpreter cost per worker.
  7. Celery/RQ latency. Reintech and Judoscale engineering posts. Median publish-to-execute ~10–50 ms, p99 100–500 ms depending on worker load. Source: reintech.io.
